# SAP 技术勘察清单（阶段 30 · AI 自查）

> **适用范围：OP 与 ES 两类目标系统（2026-09-10 扩展）。**
> **OP（经典 ABAP）**：`system_type` 传 `on_premise`（私有云传 `private_cloud`）。
> **ES（S/4HANA Cloud ABAP 环境 / ABAP Cloud，含 RAP 开发）**：公有云传 `public_cloud`。
> OP 下 Clean Core 判断基准（C 级能用但不推荐）见 F3 与 `02 - 模板/SAP资料源与降级策略.md`；
> **ES 下 Clean Core 是硬约束**，勘察走本文的「ES/ABAP Cloud 专项勘察」节。

> **本文件的定位：顾问答不了的问题，由 AI 自己查。**
>
> `需求澄清清单.md`（2A）问的是**业务语言**——顾问能答，也必须由顾问答。
> 本清单（2B）查的是**技术语言**——SAP 标准能不能做、数据落在哪张表、表之间怎么连。
> **这些问题不该问顾问**：问了他答不上来，只能得到一句"系统里应该有"，
> 然后开发去猜，猜错了无人能验证。
>
> SAP 不是从零建系统，是**在既有系统上做增量**。
> 所以 SAP 的 FS 必须回答三类顾问答不了的问题：
> **标准能不能做 / 数据在哪个表 / 表之间怎么连。**

## 三级数据源与降级策略

> 不是每个项目都能连上客户系统。查不到时**降级但不放弃**，
> 关键是**必须标注数据来自哪一级**——L3 的结论要标「待系统核实」。

| 级别 | 数据源 | 能拿到什么 | 可信度 |
|---|---|---|---|
| **L1 直连系统** | ARC-1 MCP（SAPRead / SAPSearch / SAPManage probe）读 DDIC / 表数据量 / 已有对象 | 真实表结构、真实数据量、客户实际开了哪些模块 | 最高 |
| **L2 官方检索** | sap-docs MCP（`sap_search_objects` / `sap_get_object_details` / `search`） | 标准对象清单、**Clean Core 级别**、后继对象、标准配置路径 | 高（官方口径） |
| **L3 内置常识** | AI 自身的 SAP 知识（VBAK/VBAP/MARA 等常用表） | 通用表结构估算 | **仅供参考，必须标注** |

> **MCP 工具链口径（2026-09-10 定）**：**L1 直连 = ARC-1 MCP**（对象读 / 搜索 / 探测，basic auth 直连；
> ES/ABAP Cloud 系统同样适用，ADT-only 通道），**L2 官方检索 = sap-docs MCP**
> （SAP 官方文档 / 对象库 / Clean Core 级别）。两个 MCP 同一家出品（Marian Zeis），**配套使用**——
> ARC-1 查客户系统里"有什么"，sap-docs 查官方口径"是什么 / 该用什么"。

**降级规则**：
1. 每个勘察项**优先走 L1**，连不上系统就 L2，都没有才 L3
2. **每条勘察结论必须标注来源级别**（`[L1]` / `[L2]` / `[L3-待核实]`）
3. L3 结论进入 FS 文档时，同步登记到「待确认项」，负责人写「开发（系统核实）」
4. **L1 需要客户系统连接**——连接前置确认见 `02 - 模板/SAP资料源与降级策略.md`
5. **关键结论双源验证**——凡要写进 FS 的表 / 字段 / 关联路径，至少两个独立来源相互印证；
   对不上不许二选一硬写，降级为待确认。
   （35 拿 30 当靶子——**靶子错了，拷打越狠错得越远。**）

# E 组 · 标准方案勘察

## E1 · 标准配置能不能实现【必查】

**为什么查**：这是 SAP 项目的**第一原则**——能用配置解决的不要写代码。
写出来的代码是资产也是负债：每次升级要回归、要人维护、可能触发安全红线。

**怎么查**（L2 优先）：
- 用 `search` 检索该业务的标准配置路径（英文查询，带产品范围）
- 用 `sap_search_objects` 按应用组件（如 `SD-SLS`、`MM-PUR`、`FI-GL`）找标准对象

**必须得到的结论**：

| 项 | 内容 |
|---|---|
| 标准方案 | SAP 是否有标准功能覆盖？标准事务码是什么？ |
| 配置路径 | 如果靠配置实现，SPRO 路径是什么？ |
| 差距 | 标准方案满足不了的是哪几点？**逐条列，不要笼统说"不满足"** |
| 结论 | 纯配置 / 配置+少量开发 / 必须自开发 |

> **「标准不满足，所以要开发」这句话不合格。**
> 必须说清"哪一点不满足"——否则没人能判断是不是真不满足，
> 还是没人仔细找过。这是 SAP 项目最常见的返工源头。

# F 组 · 数据落点勘察

## F1 · 业务对象 → SAP 标准表 / 视图【必查】

**查什么**：顾问说的每个业务对象，对应 SAP 里哪个表或 CDS 视图。

**怎么查**：
- L1：直连系统查 DDIC（`DD02L` / `DD03L`），或查客户已有的自开发表

**输出**：业务对象 ↔ SAP 技术对象 对照表。

## F3 · Clean Core 合规级别【必查 · 但仅供参考，不构成约束】

> ⚠️ **2026-09-07 立场修正**：
> **OP 下 Clean Core 要求是参考，不是必须。不要为了合规增加实施复杂度。**
> 除非顾问/客户明确提出要求，否则**默认用最直接、最省事的对象**。
>
> 上一版把 F3 写成了"选型的约束"——那是把 Cloud 的标准套到了 OP 上，
> 结果是拿合规绑架实施。已修正。

**查什么**：每个要用到的 SAP 标准对象，查它的 **Release State 和 Clean Core 级别**。

**怎么查**（L2）：`sap_get_object_details(object_type="TABL", object_name="<表名>", system_type="on_premise")`

**为什么仍然每次都查**：一次 MCP 调用，成本极低。
查到的级别**记录在 FS 第 3.4 节**——它**不决定这次用什么**，
但**未来客户要上 Cloud / 做升级评估时，这份记录是直接可用的依据**。
不查，将来就什么都没有。

**级别含义（On-Premise 语境）**：

| 级别 | 含义 | **OP 下怎么用** |
|---|---|---|
| **A** | Released API | ✅ 可用；**有实质理由时优先**（见下） |
| **B** | Classic API | ✅ **可用**（OP 专属） |
| **C** | Internal / Stable | ✅ **默认就用它**——这是绝大多数 SAP 标准表的级别 |
| **D** | No API | ❌ 不用 |

> **OP 下的默认立场：用最直接、最省事的对象。**
> C 级不是"问题"，是**常态**——`VBAK`/`VBAP`/`LIPS`/`VBRK`/`VBFA`/`BSEG` 全是 C 级。
> 为了避开 C 级强行上 CDS 视图，往往换来**字段不全、性能调优困难、调试不便**，
> 是典型的"合规绑架实施"。

### 什么时候才优先用 A 级替代

**只有两种情况**：

| 情况 | 判据 | 例子 |
|---|---|---|
| ① **有非合规的实质理由** | 性能 / 功能完整性 / 可维护性 | **BSEG 是簇表不能 JOIN** → 用 `I_OPERATIONALACCTGDOCITEM`（CDS 可 JOIN） |
| ② **顾问 / 客户明确要求** | 有 Cloud 迁移计划、集团有 Clean Core 考核、平台级长期资产 | — |

> **① 的关键**：BSEG 那个案例，推荐理由是「**性能**」，不是「合规」。
> 这个理由**独立成立**——即使完全不考虑 Clean Core，簇表也不该直接 JOIN。
>
> ⚠️ **凡是要拿"合规"当唯一理由的，都该停下来重新想一遍：**
> **如果没有 Clean Core 这个概念，你还会这么选吗？** 答案是"不会"的话，就别这么选。

### 什么时候要主动问顾问

**默认不问**——不为此增加顾问负担。

但发现以下信号时，在 2A 补一题「本次是否要按 Clean Core 约束来做」：
- 客户提过要上 S/4 Public Cloud / BTP / 计划系统升级
- 集团层面有 Clean Core 考核指标
- 这是一个要长期维护的公共框架 / 平台级开发

**查到 C/D 级时**：顺手记下 successor 写进 FS 备查，**但不要因此改方案**。

> **实测案例**：查 `VBAK`（on_premise）→ `cleanCoreLevel: C`，`successor: I_SALESDOCUMENT`（A）
> **OP 下的正确处理**：**默认继续用 VBAK**，
> 在 FS 第 3.4 节记一行「VBAK = C 级，备选 `I_SALESDOCUMENT`（A）」备查。
> **不要**因为 A 级存在就改用 CDS——除非有性能或功能上的实质理由。

**输出**：

| 技术对象 | 类型 | Clean Core | 状态 | 备选替代（successor，备查） | **本次选用** |
|---|---|---|---|---|---|

> 最后一列从「结论」改成「**本次选用**」——强调这是一次**实施决策**，不是合规判定。

## F3+ · ES/ABAP Cloud 专项勘察（目标系统 = ES 时必做）

> 目标系统为 ES（S/4HANA Cloud ABAP 环境 / ABAP Cloud，含 RAP）时，
> F 组常规勘察之外**追加本节**；Clean Core 从「记录备查」升格为**硬约束红线**。

**查什么 / 判定基准**：

| # | 勘察项 | 内容 | 判定 |
|---|---|---|---|
| 1 | **released API 可用性** | 方案涉及的每个标准对象，逐条查是否 released（A 级）：表→released CDS view，FM/BAPI→released API | **C 级禁用**；查不到 released 替代 → 登记待确认项（负责人开发），评估自建 CDS 覆盖 |
| 2 | **CDS 可用性** | 取数字段在标准 released CDS view 是否齐备；字段缺失时能否用 extension view（released extension include）补 | 能覆盖→写明 view 名；不能→[?] 提交裁决 |
| 3 | **RAP BO 行为** | 建模对象选 managed（标准并发/锁定/草稿托管）还是 unmanaged（legacy 逻辑接管）；是否要 draft | 业务型增删改→managed 优先；对接 legacy 逻辑→unmanaged + 注明理由 |
| 4 | **服务绑定** | OData V4 UI service / Web API；服务定义→服务绑定→发布链路 | 默认 OData V4；确认消费方（Fiori Elements / 外部系统） |
| 5 | **IAM 权限** | IAM app + authorization field 是否要新建/扩展 | 列出需申请的角色目录（business catalog） |
| 6 | **工具链** | **ADT-only**：无 SE38/SE80/GUI 事务码路径；全流程 Eclipse ADT / abapGit / gCTS | FS 中不出现 GUI 事务码操作指引 |
| 7 | **传输与包** | abapGit / gCTS 传输；自建对象落客户指定包（如 S/4HANA Cloud 的 `Z*` 包规则，如包 ZFLOW） | 包名与传输方式写入 FS §3 |

**输出**：在 F3 的「本次选用」表之外，追加一张「ES 专项核查表」
（列：勘察项 / 结论 / released 状态 / 待确认项）。任何一项查不到 released 对象，
**不许静默降级用 C 级**——必须登记待确认项。

## F4 · 自开发表 vs 标准表

**查什么**：数据要落到哪里——标准表加字段、还是建自开发表？

**判定**：

| 情况 | 落点 |
|---|---|
| SAP 标准表已有该字段 | 用标准字段 |
| 标准表可 append 增强 | 走 append structure（**不是直接改标准表**） |
| 业务数据 SAP 没有地方放 | 建自开发表（`Z*` / `Y*`） |

> **红线**：不直接 INSERT / UPDATE / DELETE SAP 标准表，只走标准 FM / BAPI。
> 见 `00 - 模板/00 - 基准/01-安全红线.md`。

# G 组 · 数据关系勘察

> **这组是"系统的数据关系"——顾问完全说不清、但 FS 必须写清的部分。**

## G1 · 表间关联路径【必查】

**查什么**：表与表怎么 JOIN，主外键是什么。

**示例**（销售订单链路）：
```
VBAK-VBELN ──→ VBAP-VBELN         抬头 → 行项目
VBAP-VBELN ──→ VBEP-VBELN+POSNR   行项目 → 计划行
VBAK-KUNNR ──→ KNA1-KUNNR         订单 → 客户主数据
VBAP-MATNR ──→ MARA-MATNR         行项目 → 物料主数据
```

**输出**：文字版关联图（不画图，用缩进或箭头列出路径）。

---

## G2 · 主数据层次

**查什么**：数据按什么层级组织。

**典型层次**：
```
Client → 公司代码(BUKRS) → 工厂(WERKS) → 库存地点(LGORT)
Client → 销售组织(VKORG) → 分销渠道(VTWEG) → 产品组(SPART)
```

**为什么查**：决定权限隔离维度（对应 FS 第 7.2 节「数据隔离维度」）。

---

## G3 · 单据流 / 业务链路

**查什么**：业务在 SAP 里是怎么流转的，上游单据和下游单据分别是什么。
**每个环节的完成状态由哪个字段判定**（如交货完成 ELIKZ、清账 AUGBL）——
这是 K6 纵切第四问（"判定字段在异常下还成立吗"）的弹药，勘察时不查，拷打时就得瞎猜。

**示例**：
```
询价(VA21) → 报价(VA21) → 销售订单(VA01) → 交货(VL01N) → 开票(VF01) → 会计凭证(FB03)
```

**为什么查**：顾问说"要一个报表"，说不清数据该从哪一环取。
链路清楚了才知道：要"已开票"的数据得联到会计凭证，只看订单是不够的。

# I 组 · 扩展点勘察

## I1 · BAdI / 用户出口【必查】

**查什么**：标准功能不够时，SAP 留了哪些官方扩展点。

**怎么查**（L2）：`search` 检索 "<业务场景> BAdI" / "<事务码> user exit"

**输出**：扩展点名称、类型（BAdI / Customer Exit / BADI Enhancement Spot）、触发时机。

## I2 · 隐式增强点

**查什么**：没有官方扩展点时，隐式增强点在哪。

**注意**：隐式增强是**次选**，标准升级时可能失效，要在 FS 里写明风险。

## I3 · 标准对象修改【红线检查】

**查什么**：有没有要直接改 SAP 标准对象。

> 一旦涉及，立即停——见 `00 - 模板/00 - 基准/01-安全红线.md`。
> **不要设计绕行方案，先报给项目负责人定夺。**

# J 组 · 存量资产勘察

## J1 · 有没有现成程序可复用【必查】

**查什么**：客户系统里、或公司代码库里，有没有类似功能已经做过了。

**怎么查**：
- L1：直连系统查已有 `Z*` / `Y*` 对象
- 本地：`00 - 模板/04 - 知识库/代码资产索引.tsv`（Grep 关键词）
- 团队素材：公司 SVN 的历史程序（去重约 300 个独立程序）

**为什么查**：`00 - 模板` 的 `AGENTS.md` 硬规则和提示词模板里都写了
「**先查样例，不要重复造轮子**」。改造比新建便宜一个量级，且已过业务验证。

## J2 · 客户系统已有类似对象

**查什么**：这个客户过去做过的定制，有没有能挂上去的扩展点。
参考客户项目里已定的增强出口约定（如"公式分支统一在 `ZCL_*_FORMULA_EXIT` 的 CASE 里加"）。
