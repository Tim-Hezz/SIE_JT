## 六组必查

### 1 标准方案勘察

| 项 | 查什么 | 判定 |
|---|---|---|
| **1.1 标准配置** | 后台配置能不能实现？（给事务码 / 配置路径） | 能 → 出「配置说明」收工，不开发 |
| **1.2 标准事务码 / 标准报表** | 有没有现成的？加变式能达到 80 分吗？ | 能 → 优先推标准 |
| **1.3 覆盖不了的点** | **逐条**列出差在哪 | 写"标准不满足"**不合格**，必须说清哪几点 |

> **判据**：标准方案能覆盖 80% 却选了自研 → 必须在方案里写明理由（长度不够 / 格式特殊 / 历史包袱 / 集成要求）。

---

### 2 数据落点勘察

| 项 | 查什么 | 输出 |
|---|---|---|
| **2.1 业务对象 → 技术对象** | 每个业务对象（销售订单 / 物料 / 批次…）映射到哪张表 / CDS 视图 / BAPI / FM | 对照表（业务名 ↔ 技术名） |
| **2.2 字段技术名** | 关键字段的 DDIC 字段名与数据元素 | 字段清单（业务叫法 ↔ 技术字段名） |
| **2.3 Clean Core 级别** | 每个标准对象查级别；C/D 级记 successor | 一列标注。**OP 下只记录，不做选型约束** |
| **2.4 自开发表 vs 标准表** | 需要新字段时：标准表已有 → 用标准的；确实要建 → Z 表 | 结论 |

> **Clean Core 立场（2026-09-07 定）**：OP 场景下 `VBAK`/`VBAP`/`LIPS`/`VBRK`/`BSEG` 全是 C 级，
> **C 级是常态不是问题**。只有两种情况优先 A 级替代：
> ① 有非合规的实质理由（性能 / 功能完整性 / 可维护性，如 `BSEG` 是簇表不能 JOIN，用 CDS 是为了**性能**）；
> ② 顾问或客户明确要求（有上云计划、集团考核）。
> **自检问句：如果没有 Clean Core 这个概念，你还会这么选吗？** 答案是"不会"就别这么选。
> ⛔ **ES / ABAP Cloud 场景立场反转**：C 级是硬约束红线，必须走 released API（A 级）+ CDS view。

---

### 3 数据关系勘察

| 项 | 查什么 | 输出 |
|---|---|---|
| **3.1 表间关联路径** | 主表与从表的关联键（如 `VBAK-VBELN = VBAP-VBELN`） | 文字版路径链 |
| **3.2 主数据层次** | 组织层次：公司代码 → 工厂 → 库位 / 销售组织 → 分销渠道 | 取数范围依据 |
| **3.3 单据流 / 业务链路** | 询价 → 报价 → 订单 → 交货 → 发票 → 凭证（找出数据该从哪一环取） | 链路 + 取数位置 |

> **取数位置选错的代价**：订单数量 vs 交货数量 vs 开票数量，三者口径不同，
> 从错的一环取数 → 报表数字永远对不上账。**这一项必须写清"从哪一环取、为什么"**。

---

### 4 性能勘察

| 项 | 查什么 | 输出 |
|---|---|---|
| **4.1 索引** | 查询条件字段有没有索引（L1 查 DDIC 索引） | 有 / 无 + 影响 |
| **4.2 数据量** | 关键表的量级（万 / 百万 / 千万行） | 量级 + 预估结果集 |
| **4.3 查询陷阱** | 簇表（`BSEG`/`BSIS` 不能 JOIN）、无索引大表、全表扫描 | 风险提示 |

> 命中陷阱 → 方案里必须有应对（换 CDS / 走索引 / 分批 + 并行游标），
> 且**验收标准要加响应时间**。

---

### 5 扩展点勘察

| 项 | 查什么 | 输出 |
|---|---|---|
| **5.1 BAdI / 用户出口** | 有没有官方出口（`SAPSearch` 查 BAdI 定义 / 用户出口） | 出口清单（名称 + 位置） |
| **5.2 隐式增强点** | 标准程序的隐式增强（ENHANCEMENT-POINT / -SECTION） | 可用增强点 |
| **5.3 红线检查** | 是否涉及直接改标准对象 / 标准表 | **命中即停，报告顾问，不设计绕行** |

> **没有官方出口时要说明**——写清"找不到出口"本身是结论，不要留空。

---

### 6 存量资产勘察

| 项 | 查什么 | 输出 |
|---|---|---|
| **6.1 现成程序可复用** | 本地代码资产索引 + 客户系统已有 Z*/Y* 对象 | 复用候选（对象名 + 可复用程度） |
| **6.2 同类对象** | 客户系统有没有同类实现（同模块 / 同业务对象） | 参考对象清单 |

> **改造比新建便宜一个量级，且已过业务验证**。这一项零顾问负担，**不做等于白扔钱**。

## 勘察记录格式（落 HTML 的「勘察结论」区块）

```
【标准方案】标准配置/事务码 XXXX 可覆盖 A、B；覆盖不了 C（原因：…）→ 需开发
【数据落点】
   业务对象      → 技术对象            Clean Core  来源
   销售订单抬头  → VBAK / I_SalesDocument  C / A    [L1]
   销售订单行项  → VBAP                C          [L1]
   客户主数据    → KNA1                C          [L2]
【关联路径】VBAK-VBELN = VBAP-VBELN；KNA1-KUNNR = VBAK-KUNNR
【单据流】订单(VBAK) → 交货(LIKP/LIPS) → 发票(VBRK/VBRP)；取数自订单环节
【性能】VBAP 约 XXX 万行；VBELN 有索引；无簇表陷阱
【扩展点】BAdI: SD_SALESDOCUMENT_... （官方出口）；无红线命中
【存量复用】客户系统已有 ZSDR003（同类报表），可改造成本预估低
【待核实】字段 XXXX 技术名（L3 常识），负责人：开发（系统核实）
```

## 系统未连通时

系统连不上是**常态**（客户环境 / 权限 / 网络都可能是障碍），**不是阻塞**：

1. 勘察照做，全走 L2（官方检索）+ L3（内置常识）
2. 每条结论标 `[L2]` / `[L3-待核实]`
3. L3 结论进待核实清单，负责人「开发（系统核实）」
4. 系统连通后，开发侧第 1 步就是核实这些项

> **系统不通不影响出方案，只影响方案的确信度。** 确信度用来源级别显式表达，
> 比闷头猜然后不标注安全得多。
