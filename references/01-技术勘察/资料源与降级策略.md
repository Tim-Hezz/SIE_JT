# SAP 资料源与降级策略

> 阶段 30「SAP 技术勘察」的弹药库。
> **核心原则：查得到就查，查不到就降级，但必须标注来源级别。**

---

## 适用范围：OP 与 ES 两类目标系统（2026-09-10 扩展）

> **本工作台支持两类目标系统：**
> - **OP（经典 ABAP）**：S/4HANA OP / ECC，`system_type` 传 `on_premise`（私有云传 `private_cloud`）；
> - **ES（S/4HANA Cloud ABAP 环境 / ABAP Cloud，含 RAP 开发）**：公有云 `system_type` 传 `public_cloud`。
>
> **不要传其他值。** 目标系统在阶段 10 归整时确认（没提则标 `[?]`）。

### 这对 Clean Core 判断意味着什么（重要）

OP 与 Cloud 的合规约束**完全不同**，别把 Cloud 的标准套到 OP 上：

| 级别 | 含义 | **OP 下能不能用** | Cloud 下 |
|---|---|---|---|
| **A** | Released API | ✅ 推荐 | ✅ 必须 |
| **B** | Classic API | ✅ **可以用** | ❌ 不行 |
| **C** | Internal / Stable | ✅ **默认就用它**（绝大多数标准表都是 C 级） | ❌ 不行 |
| **D** | No API | ❌ 不用 | ❌ 不用 |

**关键差别**：
- Cloud 下 C 级是**硬约束**，必须换；
- **OP 下 C 级是常态，不是问题。** `VBAK`/`VBAP`/`LIPS`/`VBRK`/`VBFA`/`BSEG` 全是 C 级。

> ⚠️ **2026-09-07 立场修正**：
> **OP 下 Clean Core 要求是参考，不是必须——不要为了合规增加实施复杂度。**
> 除非顾问/客户明确提出要求，否则**默认用最直接、最省事的对象**。
>
> 所以 2B 的 F3 勘察在 OP 下的产出是：
> **「记录在案，供将来升级 / 上云评估时直接取用」**——
> **不是选型依据，不构成约束**。
>
> 只有在两种情况下才优先用 A 级替代：
> ① **有非合规的实质理由**——如 `BSEG` 是簇表不能 JOIN，用 CDS 是为了**性能**而非合规；
> ② **顾问 / 客户明确要求**（有 Cloud 迁移计划、集团有考核、平台级长期资产）。
>
> **自检问句：如果没有 Clean Core 这个概念，你还会这么选吗？**
> 答案是"不会"的话，就别这么选。

### OP 下仍然不能碰的

合规放宽 ≠ 没有红线。以下仍然绝对禁止：
- 直接 INSERT / UPDATE / DELETE SAP 标准表（只走标准 FM / BAPI）
- 修改 SAP 标准对象源码（走增强 / BAdI / append structure）
- 见 `00 - 模板/00 - 基准/01-安全红线.md`
>
> **重要前提：不是所有人都能连客户系统。**
> 有的项目能连（有账号、有网络、有授权），有的不能（客户管控、外网隔离、权限没批）。
> 所以 **L2 / L3 不是"降级凑合"，是「无系统模式」下的完整可用路径**——
> 本文末尾的「无系统模式」章节说明了这条路径怎么跑完整套流程。

## 三条通道

| 通道 | 级别 | 能查什么 | 怎么查 | 限制 |
|---|---|---|---|---|
| **A. 直连客户系统** | L1 | 真实表结构、真实数据量、客户已装模块、已有自开发对象 | ARC-1 MCP（SAPRead / SAPSearch / SAPManage probe）读 DDIC / 查表 | 需要系统连通 + 账号权限 |
| **B. SAP 官方检索** | L2 | 标准对象清单、Clean Core 级别、后继对象、配置路径、BAdI | sap-docs MCP（见下；与 ARC-1 同一家出品，配套使用） | 官方口径，不反映客户实际定制 |
| **C. 本地 / 团队资产** | L1~L3 | 公司历史程序、客户已有定制、团队踩坑记录 | 本地索引 + Grep | 依赖素材是否录入 |

## 通道 B · SAP 文档 MCP（三个工具）

### 1. `sap_get_object_details` —— 查单个对象的合规级别

**用途**：判断某个 SAP 标准对象能不能用、有没有更合规的替代品。

**参数**：
- `object_type`：`TABL`（表）/ `CLAS`（类）/ `DDLS`（CDS 视图）/ `INTF` / `FUGR`
- `object_name`：对象名，如 `VBAK`、`MARA`、`CL_ABAP_REGEX`
- `system_type`：`on_premise` / `private_cloud` / `public_cloud` / `btp`
  （**按客户实际系统选，选错结论会错**）

**返回**：`state`、`cleanCoreLevel`（A/B/C/D）、`applicationComponent`、
`successor`（后继对象）

**实测示例**：
```
输入：VBAK / TABL / on_premise
输出：cleanCoreLevel = C（Internal/Stable）
     successor = I_SALESDOCUMENT（DDLS，Level A，released）
```

### 2. `sap_search_objects` —— 按主题找可用标准对象

**用途**：知道要什么功能，不知道 SAP 里叫什么。

**参数**：
- `query`：业务关键词（**英文**），如 `purchase order`、`sales document`
- `app_component`：应用组件，如 `SD-SLS`、`MM-PUR`、`FI-GL`、`SD-BIL`
- `object_type`：对象类型筛选
- `clean_core_level`：`A`（只要合规的）/ `B` / `C` / `D`
- `system_type`：同上

### 3. `search` —— 检索文档与社区

**用途**：查配置路径、BAdI、实现方法、踩坑。

**参数**：
- `query`：**必须英文**（语料以英文为主，中文检索效果差）
- `product`：功能性/配置类问题用它限定产品，如 `SAP_S4HANA_ON-PREMISE`
- `abapFlavor`：ABAP 语言类问题用 `standard`/`cloud`；**功能配置类留 `auto`**

> **查询语言是英文**——这点是硬约束，中文查询返回结果质量显著下降。
> 业务术语要翻译成 SAP 标准英文术语再查（"销售订单"→`sales document`）。

---

### ⚠️ OP 下这三个工具的实际能力边界（2026-09-07 实测）

实测对象：销售订单客户物料号（SD 模块，`system_type=on_premise`）。
**结论：精确查可用，泛搜不可靠。**

| 工具 | 实测表现 | 用法建议 |
|---|---|---|
| `sap_get_object_details` | ✅ **可靠**。查 `VBAP` 返回 C 级 + successor `I_SALESDOCUMENTITEM`；查 `I_SALESDOCUMENTITEM` 返回 A 级 | **主力工具**，优先用它逐个精确查 |
| `sap_search_objects` | ⚠️ **OP 下泛搜基本不可用**。`SD-SLS` + `on_premise` 返回 **0 条**；查 BAdI（`SD` 前缀）仅返回 1 条无关结果 | **只用来按精确对象名确认**，不要当作"发现标准方案"的手段 |
| `search` | ⚠️ 能查到，但**噪声高**。查 "customer material" 返回人事主数据、运输单位等无关内容 | 关键词必须落到**技术字段名**（如 `KDMAT VBAP`），并带 `product` 限定 |

**三条硬规则（踩过坑才写下来的）**：

1. **查不到 ≠ 对象不存在。**
   实测 `KNMT`（客户物料信息记录）返回 `found: false`，但该表真实存在，
   只是 Clean Core 数据集未收录。**禁止**据此在 FS 里写"该对象不存在"——
   标 `[L3-待核实]`，改走 `search` 补证。

2. **不要指望泛搜"发现"标准方案。**
   正确姿势是：先用 AI 常识（L3）**猜出候选对象名**（如客户物料号 → `VBAP-KDMAT` / `KNMT`），
   再用 `sap_get_object_details` **逐个验证**。`sap_search_objects` 是验证工具，不是发现工具。

3. **关键词必须精确到字段名级别。**
   `customer material info record` 这种术语级查询噪声大；
   `KDMAT VBAP customer material number field` 这种字段名级查询才能命中。

> **实践结论**：2B 勘察的大部分价值来自「先猜后验」，而不是「搜索发现」。
> 这也意味着——**AI 的 SAP 常识（L3）在这里不是兜底，是检索的起点**，
> 只是最终结论必须有 L2 证据，否则标 `[L3-待核实]`。

## 通道 A · 直连客户系统（ARC-1 MCP）

**能查**：
- 表结构：`DD02L`（表清单）、`DD03L`（字段清单）
- 数据量：直接 COUNT
- 已装模块 / 版本：区分 ECC 还是 S/4HANA、Cloud 还是 On-premise
- 已有自开发对象：查 `Z*` / `Y*` 对象，避免重复造轮子

**系统连接前置确认**（`AGENTS.md` 硬规则 15）：
任务需要连 SAP 系统但当前未连通时，**先停下来让用户定夺**——
等配置好系统再执行，还是先写镜像代码待传。**不擅自假设路线。**

**已知限制**：
- 部分系统对核心表（`TRDIR`/`E070`/`REPOSRC`）屏蔽 `RFC_READ_TABLE`，
  报错**不能反推"对象不存在"**——判断对象是否存在只能用 ARC-1 的 `SAPSearch` / `SAPRead`
  （或 `SAPManage` 的 probe 动作）
- ARC-1 走 HTTP 直连（ADT 协议），无旧 VSP 的 WebSocket 握手问题；
  `sap-remote-rfc`（直连 SOAP 执行标准 FM）仍可作为 `FMODE='R'` 场景的兜底

## 降级策略

```
查某个技术对象
    ↓
试 L1（直连系统）—— 系统通吗？
    ├─ 通 → 用真实结构，标 [L1]
    └─ 不通 ↓
试 L2（SAP 官方检索）—— 查得到吗？
    ├─ 查到 → 用官方口径，标 [L2]
    └─ 查不到 ↓
L3（AI 内置常识）—— 必须标 [L3-待核实]
    ↓
同步登记到 FS 第 11 节「待确认项」
负责人写「开发（系统核实）」
```

### 关于 L3 的硬规则

**L3 不是不能用，是必须标注。** AI 内置 SAP 常识（VBAK/VBAP/MARA/KNA1 等）
对常用对象是可靠的，但有两个风险：

1. **客户版本差异**：ECC 和 S/4HANA 表结构有差异（如 S/4 里 `BSID`/`BSAD` 有视图替代）
2. **客户定制差异**：客户可能加了自开发字段、启用了非标准模块

所以 L3 结论进入 FS 文档时，**必须同时登记待确认项**，让开发连上系统后核实。

## 无系统模式（连不上客户系统时）

> **这不是"打折模式"，是一等公民路径。**
> 大部分项目在 FS 阶段其实都连不上客户系统——权限没批、网络不通、客户不给账号。
> 这套流程必须能在无系统条件下跑通并交付。

### 无系统模式下能做什么

| 勘察项 | 无系统时怎么查 | 可信度 |
|---|---|---|
| 标准方案 / 配置路径 | L2 官方检索（SAP Help） | 高 |
| SAP 技术对象 / 字段名 | L2 官方对象库 + L3 常识 | 中高 |
| **Clean Core 级别** | **L2 官方检索，完全不受影响** | 高 |
| 表间关联路径 | L3 常识 + 官方 ER 模型 | 中 |
| 扩展点 / BAdI | L2 官方检索 | 中高 |
| **索引 / 数据量** | **查不到，只能问 + 推断** | 低 → 必须拷打兜底 |
| 客户已有定制 | 查不到 | — |

**关键：Clean Core 合规判断在无系统模式下照样能做。**
它查的是 SAP 官方 release state，跟客户系统无关——
这是无系统模式下最有价值的一项，能防住最大的合规坑。

### 无系统模式的三条补强规则

1. **拷打必须更狠**。实测验证这条路断了，35 拷打就是最后防线。
   K2（边界极端值）/ K3（SAP 现实）/ K4（时间维度）逐条过，一条不能跳。
   详见 `01 - 澄清清单/需求拷打清单.md` 末尾「系统连不上时，拷打要更狠」。

2. **性能/数据量结论一律标 `[L3-待核实]`，且必须写兜底方案**。
   - 错误写法：「数据量约 8 万行，查询正常」
   - 正确写法：「预计单次 8 万行 `[L3-待核实]`；兜底——若超时，强制必填工厂+期间，
     或改后台异步执行」

3. **高风险项在交付清单里单列**，提醒开发连上系统后第一件事就是核实：
   ```
   交付时附：待系统核实清单
   - 索引情况：<哪个表的哪个字段>
   - 数据量级：<哪个表>
   - 客户定制：<有没有自开发字段影响取数>
   ```

### 无系统模式下的交付说明（给客户看）

客户 FS 文档里要显式标注，不能假装数据都是实测的：

> 本文档中的 SAP 技术信息基于 SAP 官方资料与通用实践，
> 标注 `[L3-待核实]` 的项需在项目系统环境确认后最终定稿。

**诚实标注比假装精确安全得多**——客户能接受"待确认"，
接受不了"上线后发现文档写的是错的"。

## 客户系统信息（每个项目填一次）

> `system_type` 按目标系统填：**OP → `on_premise`（私有云 `private_cloud`）/ ES → `public_cloud`**，
> 这里填具体版本、部署形态和连通性。

```
客户：<客户名>
系统：OP（on_premise） / ES（public_cloud / private_cloud）<二选一>
版本：<S/4HANA 2020 / S/4HANA 2023 / ECC 6.0 EHP8 / S/4HANA Cloud Public Edition ... >
已启用模块：<SD / MM / FI / PP / ...>
包/命名空间：<Z / Y / 其他；ES 客户填云包规则，如包 ZFLOW>
系统连通：<是（MCP 已配） / 否 → 走无系统模式>
```

> **版本差异要留意**：ECC 与 S/4HANA 的部分表结构不同
> （如 S/4 下 `BSID`/`BSAD` 建议用 `BSID_VIEW`/`BSAD_VIEW`，
> 部分业务表有 CDS 视图替代）。填了具体版本才能判断准。

> **命名空间红线**：除非项目负责人明确要求，新对象**不得使用项目专用命名空间**（如 `/XXX/`）。
> 测试用 `Y` 前缀，正式用 `Z` 前缀。
