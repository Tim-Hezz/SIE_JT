# 01 · 安全红线

> **不可变文件。** 所有项目共用，团队内任何人（含 AI）不得放宽。
> 每条都标注了来源与真实后果——这些是踩过的坑，不是理论风险。

---

## 红线 1 · 禁止直接写 SAP 标准表

**禁止**：对任何 SAP 标准表执行 `INSERT` / `UPDATE` / `MODIFY` / `DELETE`。
范围包括但不限于 `EUDB`、`RSMPTEXTS`、`TADIR`、`SMODILOG`、`CROSS`、`D347T`。

**应当**：只能调标准函数 / BAPI，让 SAP 自己写它自己的表。

**为什么**：标准表的完整性往往由**多张表共同维护**，只写其中一张会产出「看起来正常、实际残缺」的结果。

> 实例：只复制 `EUDB` 而漏掉 `RSMPTEXTS` → GUI 状态能出来，但**按钮文本全空**，
> 且没有传输记录、绕过权限与一致性校验。这类静默残缺比直接报错难排查一个量级。

**确实没有标准 API 时**：先确认，不要自行开写标准表。

---

## 红线 2 · 找 API 的判据：读源码，看有没有 GUI 依赖

远程调用（RFC / 无 GUI 会话）场景下，选函数模块前**必须读它的源码**：

- 源码里含 `RS_CORR_INSERT` → 不能用（需要传输请求弹窗，无 GUI 会中断）
- 源码里含 `CALL SCREEN` → 不能用（无 GUI 直接 dump）

> 实例：`RS_CUA_COPY` 含 `RS_CORR_INSERT` → 不可用；
> `RS_CUA_COPY_ALL` 不含 → 可用。

**远程可调用的判据**：标准 FM 需满足 `TFDIR-FMODE = 'R'`。
自建 FM 由 ADT（VS Code abapfs 扩展）/ SAP GUI（SE80/SE11/SE24 等） 创建时指定 `processingType: rfc`。

---

## 红线 3 · 禁止远程动态执行任意 ABAP 代码

**禁止**：`GENERATE SUBROUTINE POOL` 及任何形式的「传一段代码进来编译执行」的通用远程执行入口。

**为什么**：

1. 这是完整的远程代码执行通道——从脚本、Postman 甚至 Excel 都能调，比 SE38 更隐蔽。
2. **审计盲区**：代码在内存编译执行，不落仓库对象、不进版本管理、无传输请求。
   SAP 侧 RFC 审计最多记录「谁、何时、调了哪个 FM」，**不记录参数值**——执行了什么永远查不到。

**替代**：真要执行，**为具体任务建具体 FM**。签名固定、代码进版本管理、有传输记录、可审计。
成本高一点，但可控。

---

## 红线 4 · 凭据与内部网络信息不进仓库

**禁止**出现在任何会被分发的文件里：

- 账号（邮箱 / 用户名）、密码、Token
- 内网 IP、本地代理地址（如 `127.0.0.1:xxxxx`）
- 小众内部系统标识及其连接参数
- 客户未公开的业务数据

**连接参数放哪**：本机 `~/.workbuddy/mcp.json`，不进仓库、不随模板分发。

> 本模板会被打包发给同事与外部人员。默认假设：**仓库里写的东西都会被外人看到。**

---

## 红线 5 · 生产系统的边界

- 生产系统**只允许查询类操作**，需要写操作的必须走变更流程与书面批准。
- 禁止在生产系统里做调试、临时改数据、试跑未发布对象。
- 任何生产写操作，先说清影响范围（影响行数、能否回退、回退方式）。

---

## 红线 6 · 不确定就问，不要猜

以下情况**必须先确认再动手**：

- 要改的对象是标准对象或标准增强点
- 影响范围跨模块、跨系统
- 需要写标准表 / 需要新建远程可执行入口
- 需求文档（FS/FS）里没写清的边界条件

**不要为了「先把活干完」跳过这一步。** 猜错的成本远高于问一次的成本。
